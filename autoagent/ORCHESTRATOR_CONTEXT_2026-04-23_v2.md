## 3. Зачем понадобился оркестратор

Проблема:
- есть два консольных агента: **Codex** и **Claude**;
- вручную запускать их по очереди неудобно;
- при длинной работе нужно, чтобы они:
  - брали задачу автоматически;
  - работали локально в папке проекта;
  - сохраняли состояние;
  - не теряли очередь;
  - не помечали задачу как “проваленную”, если дело не в коде, а в лимите модели;
  - могли позже продолжить с контрольной точки.

Цель:
сделать **локальный минимальный оркестратор**, который:
1. хранит очередь задач;
2. знает, где находятся Codex и Claude;
3. запускает их в неинтерактивном режиме;
4. пишет результаты в файлы;
5. фиксирует текущее состояние;
6. позволяет продолжить работу после паузы, лимитов или перезапуска.

## 4. Принятые архитектурные принципы

### 4.1. Работа только локально
Проект **не подключается к репозиторию автоматически**.
Никакой автосинхронизации с GitHub не делается.
Всё работает **только в локальной папке проекта**.

### 4.2. Пошаговый режим
Разработка шла и дальше должна идти:
- пошагово;
- с обязательной проверкой;
- без широких абстрактных рефакторингов;
- с подтверждением фактов через вывод команд, логов и статусов.

### 4.3. Не трогать несвязанные изменения
В дереве проекта уже были чужие/несвязанные изменения пользователя:
- `config/collector_prompts.json`
- файлы и папки `audit/...`

Эти изменения признаны **несвязанными** с оркестратором, поэтому их нельзя трогать в рамках этой задачи.

### 4.4. Один оркестратор — два агента
Оркестратор не заменяет агентов.
Он — только координационный слой:

- **Codex** — исполнитель;
- **Claude** — ревьюер/второй агент;
- **orchestrator.py** — диспетчер, очередь, состояние, запуск, фиксация результатов.

## 9. Почему именно такие аргументы

### 9.1. По Codex
Было доказано на практике:
- режим `codex exec` работает не так, как обычный интерактивный `codex`;
- в `codex exec` **нельзя передавать** `-a/--ask-for-approval` в той схеме, в которой это делалось сначала;
- именно это стало причиной первого падения.

Следовательно:
- ошибка была не в самом оркестраторе;
- ошибка была в неверной сборке команды запуска Codex.

После проверки `codex exec --help` была собрана новая команда:
- без `-a never`;
- с `--full-auto`.

### 9.2. По Claude
Для Claude была подтверждена рабочая неинтерактивная схема:
- `--print`
- `--output-format json`
- `--permission-mode dontAsk`
- нужная модель

То есть с точки зрения **формы запуска** обе консольные утилиты были приведены к автоматизируемому виду.

## 11. Ошибки, найденные по ходу, и их смысл

### 11.1. Ошибка №1 — запуск из не той директории
Проблема:
- запуск `python orchestrator.py` был сделан из `C:\Users\user`, а не из корня проекта.

Смысл:
- скрипт не находился;
- это не ошибка кода.

Вывод:
- запускать только из корня проекта.

### 11.2. Ошибка №2 — неверные аргументы Codex
stderr показал:
- `unexpected argument '-a' found`

Смысл:
- `codex exec` не принимает `-a` в используемой схеме;
- первый запуск упал именно по этой причине.

Вывод:
- первый сбой был **не из-за лимита**.

### 11.3. Ошибка №3 — UTF-8 BOM в `orchestrator_queue.json`
После PowerShell-перезаписи очередь перестала читаться.
Ошибка:
- `Unexpected UTF-8 BOM`

Смысл:
- файл был записан с BOM;
- `load_json` читал его как обычный `utf-8`.

Вывод:
- либо писать JSON без BOM;
- либо читать через `utf-8-sig`.

Это важное архитектурное замечание для Windows-среды.

### 11.4. Ошибка №4 — лимит Codex
Позже stderr показал:
- `You've hit your usage limit`

Смысл:
- после исправления аргументов запуск дошёл до реального обращения к модели;
- дальше упёрся уже в лимит, а не в синтаксис запуска.

### 11.5. Ошибка №5 — лимит Claude
Отдельный тест Claude вернул:
- 429
- `You've hit your limit`

Смысл:
- второй агент тоже временно недоступен не по коду, а по лимиту.

## 13. Логика взаимодействия агентов

### 13.1. Роли
- **Codex** — первый исполнитель: анализ/исполнение/создание результата.
- **Claude** — второй агент: ревью/оценка/проверка.

### 13.2. Логический цикл
Целевой цикл должен быть таким:

1. Пользователь или монитор создаёт задачу.
2. Задача кладётся в `orchestrator_queue.json`.
3. Оркестратор берёт первую задачу из очереди.
4. Задача становится `active_task`.
5. Codex получает:
   - цель;
   - ограничения;
   - список входных файлов;
   - список разрешённых файлов.
6. Codex пишет:
   - stdout;
   - stderr;
   - результат в JSON.
7. Если Codex завершился нормально:
   - задача переводится в `review`.
8. Если Codex упёрся в лимит:
   - задача не должна считаться “проваленной навсегда”;
   - она должна получить специальный статус, чтобы её можно было корректно продолжить позже.
9. После Codex должен запускаться Claude:
   - в неинтерактивном JSON-режиме;
   - с ревью результата Codex.
10. После Claude задача переводится либо в:
   - `done`,
   - либо в доработку,
   - либо в отклонение.

## 14. Почему нужен специальный статус `rate_limited`

Если агент упёрся в лимит, это:
- не ошибка кода;
- не ошибка очереди;
- не ошибка задачи;
- не ошибка архитектуры;
- не причина навсегда помечать задачу как `failed`.

Поэтому в контрольной версии оркестратора введена идея:
- определять лимит по stderr/stdout;
- хранить его отдельно;
- переводить задачу в статус `rate_limited`, а не `failed`.

Это критично для надёжного восстановления работы после паузы.

## 15. Приоритеты

### Приоритет 1 — устойчивость состояния
Нельзя терять:
- очередь,
- активную задачу,
- статус,
- результаты stdout/stderr,
- причину падения.

### Приоритет 2 — корректная диагностика
Оркестратор должен различать:
- ошибку кода;
- таймаут;
- неверные аргументы;
- лимит модели;
- повреждённый JSON / BOM.

### Приоритет 3 — безопасная автоматизация
Нужно уметь:
- запускать агентов без ручного `yes`;
- при этом не делать опасных неконтролируемых действий вне проекта.

### Приоритет 4 — воспроизводимость
После перезапуска/паузы должно быть понятно:
- где всё остановилось;
- на каком агенте;
- почему;
- что нужно делать дальше.

### Приоритет 5 — расширяемость
Позже оркестратор должен уметь:
- не только запускать Codex;
- но и автоматически передавать результат в Claude;
- а потом возвращать задачу в очередь либо завершать её.

## 16. Что уже не предусмотрено заранее, но обязательно нужно учесть

Ниже важные моменты, которые легко упустить.

### 16.1. Кодировка на Windows
PowerShell и Python могут писать JSON по-разному.
Нужно стандартизировать:
- либо запись всегда без BOM;
- либо чтение через `utf-8-sig`.

### 16.2. Лимиты моделей — это не “ошибка задачи”
Это отдельный технический статус.

### 16.3. Нужно разделить “активную задачу” и “историю”
Иначе после падений будет путаница:
- где последняя попытка;
- что ещё в очереди;
- что уже было обработано.

### 16.4. Нужны отдельные артефакты запуска
stdout/stderr нельзя хранить только в памяти.
Они должны сохраняться в `.ai_logs`.

### 16.5. Нужна нормальная очистка
Позже понадобится:
- завершение задачи;
- перенос в историю;
- повторная постановка;
- сброс active_task;
- повторная попытка.

### 16.6. Нужно предусмотреть, что оба агента могут быть недоступны
Сейчас это уже подтверждено.
Следовательно оркестратор обязан:
- не рушить задачу окончательно;
- уметь честно сохранять состояние “ждём доступности агента”.

### 16.7. Нужны отдельные статусы по стадиям
Минимально:
- `queued`
- `running`
- `review`
- `done`
- `failed`
- `rate_limited`

### 16.8. Желателен механизм повторного запуска
После сброса лимитов хорошо бы иметь:
- `retry`
- или повторный `start`, если задача в `rate_limited`.

- выявлены и классифицированы ограничения среды:
  - неверные аргументы `codex exec`;
  - BOM;
  - лимиты обоих агентов.

Это не финальная система, но уже не “идея”, а рабочая контрольная база.

## 24. Общий контекст для обоих агентов: нужен ли он и как его организовать

Да, общий контекст для Codex и Claude нужен.
Без него агенты будут:
- повторять уже сделанные шаги;
- терять доказанные причины ошибок;
- конфликтовать по следующему действию;
- снова запускать уже проверенные гипотезы;
- путать “ошибку кода” и “внешнее ограничение” вроде лимита.

Но общий контекст должен быть организован **не как один хаотичный файл**, а как разделённая система контекста.

### 24.1. Рекомендуемая модель контекста

Нужно разделить контекст на 4 уровня.

#### Уровень 1. Постоянный проектный контекст
Файл:
- `AGENTS.md`

Назначение:
- мастер-правила проекта;
- архитектура;
- инварианты;
- ограничения;
- тестовый контур;
- правила правок;
- бизнес-ограничения.

Это **не журнал работы**.
Этот файл нельзя превращать в оперативный лог.

#### Уровень 2. Оперативный общий контекст работы
Рекомендуемый файл:
- `SESSION_CONTEXT.md`

Назначение:
- краткая, но точная история текущей сессии/серии сессий;
- что уже доказано;
- какие команды запускались;
- какие ошибки уже были;
- что они значат;
- на каком шаге всё остановилось;
- что должен делать следующий агент или человек.

Именно этот файл должен быть общим контекстом для обоих агентов.

#### Уровень 3. Машиночитаемое состояние
Файлы:
- `orchestrator_state.json`
- `orchestrator_queue.json`

Назначение:
- текущее состояние автоматики;
- активная задача;
- очередь;
- текущий этап;
- кто сейчас работал;
- последняя ошибка;
- служебные статусы вроде `rate_limited`.

Это не человеко-читаемый журнал, а источник истины для логики оркестратора.

#### Уровень 4. Контекст конкретной задачи
Файлы:
- `task_001.json`
- в будущем `task_002.json`, `task_003.json` и т.д.

Назначение:
- цель задачи;
- ограничения;
- входные файлы;
- разрешённые файлы;
- артефакты;
- статус конкретной задачи.

---

## 25. Почему не стоит делать один общий “свободный” файл

Один общий текстовый файл без строгой структуры опасен по трём причинам:

### 25.1. Контекст быстро превращается в мусор
Если оба агента и человек пишут туда всё подряд, через время невозможно понять:
- что факт;
- что гипотеза;
- что уже устарело;
- что относится к текущей задаче, а что к старой.

### 25.2. Можно потерять важные куски
Если один агент перезаписывает файл целиком, а не дописывает блок, можно потерять:
- прошлые выводы;
- важные доказательства;
- причины ошибок;
- результаты запуска.

### 25.3. Второй агент может принять гипотезу за факт
Если в общий файл писать не подтверждённые предположения как свершившийся вывод, второй агент начнёт строить дальнейшую работу на ложной базе.

---

## 26. Безопасная схема общего контекста

Общий контекст нужен, но должен быть **структурированным**.

### 26.1. Что должен читать каждый агент перед работой
Перед запуском каждый агент должен читать:

1. `AGENTS.md`
2. `SESSION_CONTEXT.md`
3. свою текущую задачу `task_XXX.json`
4. при необходимости:
   - `orchestrator_state.json`
   - `orchestrator_queue.json`

### 26.2. Что должен дописывать Codex
Codex не должен переписывать весь контекст.
Он должен дописывать только свой блок:

- что запускал;
- какие команды выполнял;
- какие файлы читал;
- какие файлы менял;
- какой stdout/stderr получил;
- какой результат вернул;
- что предлагает делать следующим шагом.

### 26.3. Что должен дописывать Claude
Claude также не должен переписывать весь контекст.
Он должен дописывать только свой блок:

- что проверил;
- какие риски увидел;
- какой вердикт дал;
- что принять;
- что отклонить;
- что делать следующим шагом.

### 26.4. Что должен делать человек
Человек должен:
- подтверждать опасные действия;
- фиксировать управленческие решения;
- отделять “рабочий факт” от “идеи на будущее”.

## 27. Рекомендуемый новый файл: SESSION_CONTEXT.md

Для устойчивой работы оркестратора рекомендуется создать отдельный файл:

- `SESSION_CONTEXT.md`

### 27.1. Его назначение
Это должен быть **оперативный общий журнал контекста** для:
- Codex;
- Claude;
- человека;
- будущего восстановления работы после паузы, лимитов или перезапуска.

### 27.2. Что в нём должно быть обязательно
Рекомендуемая структура:

1. **Текущая контрольная точка**
2. **Что подтверждено фактами**
3. **Что уже пробовали**
4. **Какие ошибки были**
5. **Что означает каждая ошибка**
6. **Какие команды уже запускались**
7. **Какие артефакты созданы**
8. **Что нельзя трогать**
9. **Какие несвязанные изменения есть в дереве**
10. **Следующий шаг**
11. **Блок Codex**
12. **Блок Claude**
13. **Блок решений человека**

### 27.3. Почему это полезно
Такой файл:
- уменьшает повторную работу;
- защищает от потери контекста;
- помогает продолжить работу после лимитов;
- делает взаимодействие агентов последовательным;
- позволяет быстро восстановиться “с нуля”.

## 28. Как это встроить в будущую архитектуру оркестратора

Целевой вариант архитектуры должен быть таким:

```text
AGENTS.md                -> постоянные правила проекта
SESSION_CONTEXT.md       -> общий оперативный контекст
task_XXX.json            -> контракт конкретной задачи
orchestrator_state.json  -> машинное текущее состояние
orchestrator_queue.json  -> очередь и active_task
.ai_logs/*               -> stdout/stderr/результаты запусков
.ai_reviews/*            -> ревью и вердикты
```

### 28.1. Логика чтения
Перед запуском агента оркестратор в будущем должен формировать контекст запуска из:
- `AGENTS.md`
- `SESSION_CONTEXT.md`
- активной задачи
- последних логов по этой задаче

### 28.2. Логика записи
После завершения шага:
- машинный результат идёт в JSON и `.ai_logs`;
- краткий осмысленный итог шага дописывается в `SESSION_CONTEXT.md`.

## 29. Навредит ли это проекту

При правильной реализации — **нет, не навредит**.

Наоборот, это один из ключевых элементов нормальной многоагентной работы.

Польза:
- единая линия рассуждения;
- меньше повторов;
- меньше ложных откатов;
- ясная история решения;
- устойчивость после паузы;
- проще аудит и продолжение работы через дни или недели.

Навредить это может только если:
- дать агентам хаотично переписывать один и тот же файл;
- не разделять факты и гипотезы;
- не отделять постоянный контекст от оперативного.

## 30. Практическое решение для следующего этапа

Следующим логичным шагом после восстановления лимитов должно быть:

1. создать `SESSION_CONTEXT.md`;
2. зафиксировать шаблон его структуры;
3. определить, какие разделы может писать Codex;
4. определить, какие разделы может писать Claude;
5. вшить в оркестратор правило:
   - перед запуском читать контекст;
   - после завершения шага дописывать краткий итог.

Итог:
**общий контекст для обоих агентов нужен обязательно, но только в структурированном виде и как отдельный оперативный файл, а не как хаотичный общий блок текста.**
