## 2. Как работает текущая классификация

```python
# debt_monitor.py → classify_debtors()

for каждого клиента:
    opening = float(row.get("opening", 0))
    debit   = float(row.get("debit", 0))
    credit  = float(row.get("credit", 0))
    days    = int(row.get("days_silence", 0))   # из JSON 1C

    # ФИЛЬТР 1: реальный долг (не рябь 1С)
    if opening < 100 or debit <= 0:
        level = 0  # skip
        continue

    # ФИЛЬТР 2: уровень по дням
    if days < 10:
        level = 0  # skip
    elif days < 15:
        level = 1
    ...
    elif days >= 30:
        level = 5

    # ПОВЫШЕНИЕ: violation_shipment
    violation_shipment = (opening >= 100 and debit > 0 and days >= 7)
    if level == 0 and violation_shipment:
        level = 1   # КЛЮЧЕВОЙ ИСТОЧНИК ЗАВЫШЕНИЯ
```

### Real days (в engine, не в monitor)
```python
# collections_engine.py
if dry_run:
    real_days = 0  # в dry-run days_1c используются напрямую
else:
    real_days = get_debt_days_since_first_seen(name)
    real_days = min(real_days, days_1c + 7)   # FIX-3 cap
```

## 6. Дубли и переучёт

### Нет дублей на уровне клиентов
`load_latest_debt_json()` берёт один (последний) файл из каждой группы. Одно юрлицо не повторяется.

### Переучёт через violation_shipment
Клиенты с 7–9 днями просрочки, которые ещё покупают (debit > 0):
- По classify_debtors → level 1 (завышено)
- В engine: FIX-1 guard фильтрует (`debit > 0 OR credit > 0 → "активны" → skip`)
- **Итог: переучёт в classify_debtors, но engine его нейтрализует**
- Классификатор показывает завышенное число "level 1", engine правильно их блокирует

### first_seen инфляция (источник инцидента 2026-04-10)
- 157 клиентов с `first_seen = 2026-03-19` (дата первого запуска коллектора)
- На 10.04.2026: `real_days = today - first_seen = 22 дня` для ВСЕХ этих клиентов
- FIX-3 cap `min(real_days, days_1c + 7)` ограничивает, но не устраняет проблему
- Без FIX-3: клиент с days_1c=12 получал real_days=22 → уровень 3 вместо 1
