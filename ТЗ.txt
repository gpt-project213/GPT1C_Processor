ТЗ: привести систему коллектора, WhatsApp-оповещений и менеджерских диалогов в устойчивое рабочее состояние
0. Роль

Ты — не рефакторщик ради красоты и не “помощник с идеями”.
Ты — инженер по восстановлению и доводке production-механики взыскания.

Твоя задача:

разобрать всю цепочку коллектора;
найти все реальные причины блокировок, зависаний, молчания и неэффективности;
перепроектировать только проблемные узлы;
внедрить правки точечно, безопасно, полноценно;
добиться того, чтобы система работала без зависания на одном менеджере, одном клиенте или одном состоянии.
1. Цель

Сделать так, чтобы:

Ни один менеджерский диалог не мог блокировать весь поток клиентов менеджера.
Ни одно молчание менеджера не останавливало работу системы.
Ни один клиент не терялся из-за зависшего state.
WhatsApp-оповещения реально доходили до стадии отправки, а не умирали в ожидании подтверждений.
Все зависшие, устаревшие, конфликтные состояния автоматически разруливались, а не висели неделями.
После молчания менеджеров решение переходило ко мне/админу, а не оставалось висеть.
У менеджеров не оставалось ничего зависшего навсегда.
Система работала как конвейер, а не как fragile-диалог с одной точкой отказа.
2. Главный принцип
Ничего не ломать из того, что реально работает.

Но:

если текущая логика приводит к блокировке;
если state делает очередь мёртвой;
если архитектурно один зависший диалог убивает весь поток;
если менеджер не отвечает и всё стоит;
если уведомления уходят, но взыскание не движется;

то такие части нужно исправлять, а не беречь.

5. Что нужно найти

Нужно не “один баг исправить”, а найти весь набор причин, почему система неэффективна.

Обязательно выявить:

A. Блокировки потока
один активный диалог на менеджера
зависший CONFIRMED
зависший AWAITING_CONFIRM
зависший phone_pending
зависшие напоминания
зависшие callbacks
старые manager_msg_id, которые больше не должны держать состояние
B. Блокировки по state
вечные pending
несбрасываемые флаги
логика “уже отправлено”, которая убивает повтор
holiday_flags / daily flags / sent flags
конфликт между разными json-state
C. Блокировки по данным
телефон есть, но _needs_phone = true
клиент в clients.json, но не попадает в коммуникацию
клиент в debtors_contacts.json, но state ждёт другого шага
конфликт display_name / client_name / confirmed_name
D. Блокировки по людям
менеджер молчит
менеджер ответил неоднозначно
менеджер ответил не на тот сценарий
менеджер забыл номер
менеджер не нажал кнопку
менеджер вообще не пользуется этой веткой
E. Блокировки по архитектуре
один диалог = один менеджер = весь поток стоит
WhatsApp ждёт Telegram-решения слишком долго
нет fallback-сценария
нет таймаута жизненного цикла диалога
нет эскалации после молчания
нет “разморозки” очереди
6. Целевое состояние системы

Вот до чего нужно довести механику.

6.1. Ни один клиент не должен висеть бесконечно

Для любого клиента должен существовать конечный жизненный цикл:

создан → обработан → подтверждён / отклонён / эскалирован / закрыт / отложен с TTL

Нельзя допускать:

бессрочный AWAITING_CONFIRM
бессрочный CONFIRMED
бессрочный pending phone
бессрочный manager waiting
6.2. Один менеджер не должен блокировать весь поток

Текущую архитектуру “один активный диалог на одного менеджера” нужно пересмотреть так, чтобы:

либо система поддерживала безопасную очередь;
либо зависший диалог не мешал следующим клиентам;
либо новые клиенты уходили в очередь с TTL и эскалацией;
либо зависший диалог автоматически закрывался/эскалировался после таймаута.

Но в любом случае:

один молчащий менеджер ≠ остановка всего взыскания по его клиентам
6.3. После молчания решение должно переходить ко мне

Нужна жёсткая логика:

Если менеджер:

не ответил;
не подтвердил телефон;
не нажал “отправить”;
не завершил диалог в течение заданного окна;

то:

диалог не висит вечно;
система не блокируется;
решение переходит ко мне / админу;
менеджерская ветка помечается завершённой или просроченной;
клиент движется дальше по понятному сценарию.
6.4. У менеджеров ничего не должно висеть вечно

Любой менеджерский pending должен иметь:

timestamp создания;
timestamp последнего действия;
TTL;
причину блокировки;
автоматическую развязку;
результат по истечении таймаута.
6.5. WhatsApp должен работать как конвейер

Система должна различать:

готов к отправке
нет телефона
телефон требует подтверждения
менеджер не ответил
эскалация админу
отправлено
ошибка доставки
повтор по регламенту
закрыто

Нельзя допускать “серой зоны”, где непонятно, что с клиентом.

8. Обязательные функциональные изменения

Ниже — то, что должно быть реализовано, если анализ подтвердит проблему.

8.1. Таймауты всех зависающих состояний

Ввести TTL/auto-expire для:

AWAITING_CONFIRM
CONFIRMED без телефона
phone_pending
awaiting_send
любых похожих промежуточных состояний

После TTL:

либо закрытие;
либо эскалация;
либо перевод в очередь администратора;
либо перевод в следующую автоматическую стадию.
8.2. Разблокировка потока менеджера

Нужно убрать или обойти блокировку типа:

один активный диалог → всё остальное стоит

Нужен один из вариантов:

безопасная очередь диалогов на менеджера;
несколько независимых контекстов по client_id;
авто-завершение старого контекста;
маршрутизация ответов по message_id / callback / session;
отдельный диспетчер очереди менеджера.

Главное:

следующие клиенты должны продолжать обрабатываться
8.3. Админское решение после молчания

После N часов / дней без ответа менеджера:

клиент автоматически попадает ко мне;
мне даётся карточка решения;
менеджер больше не держит этого клиента;
это фиксируется в state и логах.
8.4. Нет телефона ≠ остановка навсегда

Для клиентов без телефона:

уведомление менеджеру;
TTL ожидания;
если менеджер не дал номер — переход ко мне;
возможность пометить клиента как “нет контакта / не удалось получить / отложить на X дней / исключение”.
8.5. Санация противоречивых данных

Исправить логику конфликтов:

телефон есть, но _needs_phone = true
имя подтверждено, но диалог не считается завершённым
клиент завершён, но всё ещё pending
state противоречит registry
registry противоречит contacts
contacts противоречит clients

Нужна нормализация и единые правила приоритета.

8.6. Полная наблюдаемость

Добавить достаточное логирование:

кто завис
где завис
почему завис
сколько висит
кто держит блокировку
что сработало по TTL
кому ушла эскалация
почему WhatsApp не отправился
какой клиент в какой стадии
9. Что в конце должно получиться

Ты должен довести систему до состояния, где можно честно сказать:

Менеджер не может случайно или молча заблокировать весь поток.
Старые диалоги не висят бесконечно.
Все решения после молчания менеджеров переходят мне.
WhatsApp-оповещения реально доходят до стадии отправки.
Нет “мёртвых клиентов”, про которых забыли.
Нет “молчаливых pending-state”.
Нет вечных флагов “ждём”.
Любой клиент имеет прозрачный, конечный жизненный цикл.
Любой тупик либо автоматом развязывается, либо эскалируется.
У менеджеров не копится цифровое болото из незавершённых диалогов.

C. Что было изменено

G. Какие тесты/проверки выполнены
H. Какие state-сценарии теперь автоматически разруливаются
I. Подтверждение, что блокировка менеджером больше не убивает поток
J. Подтверждение, что молчание переводит решение ко мне
11. Жёсткий запрет

Запрещено:

чинить только Ергали и считать задачу выполненной;
лечить только один файл;
делать косметику без решения архитектурной причины;
оставлять зависания “на потом”;
делать вид, что всё работает, если есть хоть одна вечная блокировка;
предлагать вручную каждый раз чистить json/state как основное решение.

Решение должно быть системным, а не разовым.
