# ПОЛНЫЙ ОБЪЕДИНЁННЫЙ СВОД АУДИТА ПРОЕКТА GPT1C_Processor / AI 1C PRO

Дата: 13.04.2026. Источники: поверхностный аудит (9 слоёв + конфиги/тесты), глубокий анализ (race conditions, dead code, callback routing, pipeline data loss, security). Ни одной правки не внесено.

---

## I. ПРЕИМУЩЕСТВА

1. **Архитектура 9 слоёв** — разделение: парсинг → отчёт → аналитика → AI → оркестрация → бот → коллектор. Зависимости строго вверх.
2. **Атомарность записи** — почти везде `NamedTemporaryFile`/`mkstemp` + `os.replace` для JSON; очередь через rename `.xlsx` → `.xlsx.work`.
3. **Продакшн-система** — реальный бизнес, 5+ менеджеров, бухгалтер Саида, WhatsApp-коллектор, 30+ jobs, ролевая модель.
4. **Timezone** — `ZoneInfo(os.getenv("TZ", "Asia/Almaty"))` с `load_dotenv` почти везде; нарушений `timezone(timedelta(hours=5))` не обнаружено.
5. **Тесты** — 4 файла, ~370 проверок (импорты, хелперы, коллектор, парсеры).
6. **Документация** — `CLAUDE.md`, `SESSION_CONTEXT.md`, история фиксов, карта архитектуры.
7. **Коллектор** — полная цепочка: классификация → DeepSeek → батч → менеджер → админ → WhatsApp.

## II. КРИТИЧЕСКИЕ БАГИ (9 штук)

### B1 / CRIT-1: `voice_calls.py` — NameError при плохом env

- **Файл:** `collector/voice_calls.py:40-50`
- **Суть:** `logger.warning(...)` в строке 46, но `logger = logging.getLogger(__name__)` в строке 50. При ошибке парсинга env (например `COLLECTOR_CALL_LEVEL=abc`) — `NameError`, модуль не импортируется, каскадно убивает `collections_engine.py`.
- **Вероятность:** 100% при ошибке в `.env`.

### B2: `collection_agent.py` — KeyError в fallback шаблонах

- **Файл:** `collector/collection_agent.py:318-324`
- **Суть:** При ошибке DeepSeek вызывается `_get_fallback_template(msg_type).format(...)`. Шаблоны содержат плейсхолдеры `{report_date_part}`, `{days_text}`, которых нет в переданных kwargs.
- **Верификация:** проверка показала, что `_get_fallback_template` (строки 98-127) **сама** добавляет `report_date_part` и `days_text` через kwargs. **Баг снимается** — в вызове из строки 274 передаётся `report_date=report_date`, и функция обрабатывает его. Но при вызове из строки 320 kwargs пустые (вызов из пути msg_type=""), и `_get_fallback_template` вызывается с `**kwargs` = пустыми строками. **Итог:** баг отсутствует в текущей версии.

### B3: `config.py` — строковый chat_id → None

- **Файл:** `config.py:141-142`
- **Суть:** `int(val) if isinstance(val, int) else None` — если в `managers.json` значение `chat_id` записано строкой (`"12345"`), менеджер получает `chat_id=None` и не находится.
- **Следствие:** менеджер выпадает из маршрутизации отчётов.

### B4 / DEAD-1: `manager_dialog.py` — 120 строк мёртвого кода

- **Файл:** `collector/manager_dialog.py:393-523`
- **Суть:** `_send_whatsapp_and_notify` сразу `return False` (строка 404). Код строк 406-523 (import asyncio, send_whatsapp, retry loop, update_after_contact, start_client_dialog, уведомления наблюдателей) — **никогда не выполняется**.
- **Следствие:** вся логика отправки WA через менеджерский диалог заблокирована; функция всегда возвращает False.

### B5: `revenue_concentration_report.py` — дедупликация по несуществующему полю

- **Файл:** `revenue_concentration_report.py:150-152`
- **Суть:** Дедупликация сравнивает `c.get("revenue", 0.0)`, а в JSON от `sales_parser.py` поле называется `"total"`. Revenue всегда 0, побеждает произвольный клиент из дублей.

### B6: `rfm_clients_report.py` — та же ошибка revenue vs total

- **Файл:** `rfm_clients_report.py:174-179`
- **Суть:** Аналогично B5. `merged_revenue` считается по `revenue` = всегда 0. Однако в строке 232 данные берутся по `"total"` корректно, а в 244 сохраняются как `"revenue"`. Итог: дедупликация сломана, но итоговый отчёт строится по правильному полю.

### CRIT-2: `.xlsx.work` застревают навсегда

- **Файл:** `run_pipeline_all_mp.py:394-404, 436-440`
- **Суть:** `_iter_queue` ищет `*.xlsx`. После claim (`rename .xlsx → .xlsx.work`) при crash/kill файл остаётся как `.work`. Glob его не видит. Лог пишет "preserved in queue for retry", но retry **никогда не произойдёт**.
- **Следствие:** отчёт полностью теряется без ручного переименования.
- **Вероятность:** каждый kill -9, OOM, перезагрузка.

### CRIT-3: `dso_aging_report.py` — fallback на closing

- **Файл:** `dso_aging_report.py:170-172`
- **Суть:** `"debt": c.get("debt", c.get("closing"))` — fallback на `closing`, прямое нарушение инварианта CLAUDE.md ("Debt key: always debt, never closing — source of past analytics bugs").

### B3-ext: `dso_aging_report.py` — второй fallback на closing

- **Файл:** `dso_aging_report.py:312`
- **Суть:** Аналогичный fallback в другом месте того же файла.

## III. ВЫСОКИЕ РИСКИ (11 штук)

### R1: `send_tg.py` — ADMIN_CHAT_ID обязателен

- **Файл:** `send_tg.py:103-104`
- **Суть:** `_assert_ready()` требует `ADMIN_CHAT_ID` даже при явном `chat_id`. Сценарий «отправка только по chat_id без админа» — падение.

### R2: `ai_analyzer.py` — нет retry API

- **Файл:** `ai_analyzer.py:287-309`
- **Суть:** Один вызов API без ретраев. При ошибке — `RuntimeError`, потеря отчёта.

### R3: `debt_auto_report.py` — find_header возвращает [0,1]

- **Файл:** `debt_auto_report.py:307`
- **Суть:** При неудаче возвращает `[0, 1]` вместо исключения. На кривом extended-файле — тихий разбор мусорных строк.

### R4: `debt_monitor.py` — date.today() без TZ

- **Файл:** `collector/debt_monitor.py:245`
- **Суть:** `date.today()` использует локальное время, а не Asia/Almaty. Расхождение на границе суток (UTC+5).

### R5: `registry_manager.py` — телефон клиента в логе

- **Файл:** `collector/registry_manager.py:122`
- **Суть:** Номер телефона попадает в лог. Нарушение CLAUDE.md.

### R6 / HIGH-3: JSON-хранилища без блокировок (8 файлов)

- **Файлы:** `collector_state.json`, `collector_dialogs.json`, `wa_approval_batches.json`, `saida_payment_holds.json`, `debt_stop_registry.json`, `deletion_queue.json`, `debtors_contacts.json`, `user_analytics.json`
- **Суть:** Load → modify → save без file lock. Два параллельных процесса (бот + subprocess коллектора, или бот + APScheduler job) — lost update, последний `replace` побеждает.
- **Самый опасный:** `wa_approval_batches.json` — два менеджера жмут кнопки одновременно, решение одного теряется.

### HIGH-1: revenue vs total — дедупликация сломана в двух файлах

- **Файлы:** `rfm_clients_report.py:174`, `revenue_concentration_report.py:150`
- **Суть:** см. B5/B6. Дедупликация выбирает произвольного клиента из дублей вместо максимального.

### HIGH-2: `debt_stop_control.py` — фиксированный `.tmp`

- **Файл:** `bot/debt_stop_control.py:87-92`
- **Суть:** `_save_json` использует `path.with_suffix(".tmp")` — всегда один и тот же файл. Два параллельных вызова пишут в один `.tmp` — повреждение JSON.

### HIGH-4: Неатомарные записи HTML/JSON в генераторах

- **Файлы:** `debt_auto_report.py`, `sales_report.py`, `gross_report.py`, `inventory.py`, `expenses_parser.py`
- **Суть:** `Path.write_text()` без temp+replace. При обрыве (kill, OOM) — битый HTML или JSON.

### HIGH-5: `send_reports.py` — inventory без проверки роли

- **Файл:** `bot/send_reports.py:~4248-4262`
- **Суть:** `force_report_to_user` для `inventory` — нет проверки роли. Плюс `send_with_acl` для "ОСТАТКИ" разрешает сводный не-админу. Любой chat_id может получить сводку остатков.

### HIGH-5b: Роль `unknown` — меню менеджера

- **Файл:** `bot/send_reports.py:~2875-2883`
- **Суть:** Ветка `else` в определении клавиатуры строит `kb_main` как для менеджера с `my_name = "Unknown"`.

## IV. ПОТЕРЯ ДАННЫХ ПРИ СБОЯХ ПАЙПЛАЙНА

### P1: Частичный xlsx при crash записи в IMAP

- **Файл:** `imap_fetcher.py:279-282, 541-557`
- **Суть:** `open + write` без temp+rename. При crash — неполный xlsx в queue.
- **Восстановление:** ручное удаление + повторная выгрузка.

### P2: Повторный fetch при пустом письме

- **Файл:** `imap_fetcher.py:574-578`
- **Суть:** Если ничего не сохранено (found_any=False), письмо только `\Seen`, не `\Deleted`. При следующем `--once` — дубликаты `(n)` в queue.

### P3: .work застревают (= CRIT-2)

- **Файл:** `run_pipeline_all_mp.py:394-404, 436-440`

### P4: Рассинхрон JSON/HTML

- **Файлы:** `inventory.py:354-407`, `expenses_parser.py:686-687`
- **Суть:** JSON сохраняется, затем HTML. При обрыве между ними — JSON есть, HTML нет (или наоборот).

### P5: Нет `sales_*.json` при обработке только `run_pipeline_all_mp`

- **Суть:** `run_pipeline_all_mp` вызывает `sales_report` (HTML), но не `sales_parser` (JSON). В `send_reports.py` после clean вызываются парсеры. Аналитика без JSON продаж.

### P6: Битый JSON в аналитике

- **Файлы:** все 6 скриптов Layer 5
- **Суть:** `json.load` падает; скрипты пропускают файл с warning, ищут следующий. Деградация, не крах.

### P7: AI обрыв записи

- **Файл:** `ai_analyzer.py:311-324`
- **Суть:** `write_text` не атомарен. Битый `.txt` при обрыве.

## IX. RACE CONDITIONS — КАРТА ПАРАЛЛЕЛЬНОГО ДОСТУПА

**Исполнители:**
- Главный цикл бота (async handlers)
- APScheduler jobs (thread pool)
- WhatsApp poller (async job)
- `python -m collector.collections_engine` (отдельный subprocess)
- `run_pipeline_all_mp.py` (subprocess) — к state JSON не обращается

| `collector_state.json` | бот + subprocess коллектора | Нет | Lost update |

## X. АРХИТЕКТУРНЫЕ ПРОБЛЕМЫ

1. **Монолит `send_reports.py`** — ~7656 строк: UI, ACL, архив, AI, CRM, коллектор, debt_stop, 30+ jobs, 40+ callback prefixes. Невозможно тестировать изолированно.
2. **Два контура стоп-отгрузки не синхронизированы:**
   - Контур A: `debt_stop_control` + `debt_stop_registry.json` (3 кнопки админу: clear, keep, conditional)
   - Контур B: `shipment_control` + `collector_shipment_decisions.json` (4 кнопки менеджеру: allow, allow_after, block_until, block)
   - `collections_engine` не знает о контуре B
3. **Шаблоны не наследуют `base.html`** — дублирование CSS/разметки в 7 шаблонах.
4. **Слой 5 — HTML через f-strings** и `{{`/`}}`, не Jinja.
5. **`inject_local.py` — неверный ROOT** — `Path(__file__).parent` = `bot/`, QUEUE_DIR указывает на `bot/reports/queue` вместо `reports/queue`.
6. **3 реализации записи `deletion_queue.json`** — `send_reports._save_deletion_queue`, `debt_stop_control._save_json`, `client_dialog._schedule_tg_deletion` — разные стратегии атомарности.
